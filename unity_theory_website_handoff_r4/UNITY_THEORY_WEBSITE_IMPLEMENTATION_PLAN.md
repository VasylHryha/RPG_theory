## 2. Product goal and scientific meaning

### 2.1 The reader's journey

The first screen answers **“What is this project investigating?”**, not “What is a response kernel?” The journey is:

```text
A familiar phenomenon
→ parts / arrangement / behaviour
→ a persistent whole and the activity still inside it
→ geometry and dynamics influencing one another
→ a whole becoming a useful component of another system
→ structures changing conditions for further structures
→ effective interactions that may help stabilize further organization
→ the proposed general pattern
→ definitions, evidence, model calculations and tests
```

There are three visible entry points: **Start simply**, **Read the framework**, **Explore the documents**. Advanced readers may skip directly to technical material. Neither a slide deck nor a PDF is required to understand the site.

The broad geometry–dynamics/recursive-organization question stays visible. The predictive-representation programme may appear **as a historical/proposed test track if retained by the current sources or explicitly selected by the owner**. Fundamental interaction unification remains an explicitly open ambition, not a proven result and not something silently erased to make the programme easier.

### 2.3 Current scientific boundaries to carry into every layer

As inherited explanatory intent, retain geometry as arrangement/relations/constraints and the temporal side as more than one Hertz value; bind the precise current wording only after reading the locked core. Retain the distinction between lower-level activity and a higher-level description. Keep environmental feedback and possible further organization in the explanation.

The historical audit supplies the following editorial safeguards to check against the current documents, not a replacement core: self-consistency alone does not prove stability; stability is not always asymptotic return; conservative bounded motion and dissipative attraction differ; some modes describe relaxation rather than periodic oscillation; an action is not automatically potential energy; eliminating variables can introduce memory and effective forcing; coarse-graining is not physical creation of an object; scale flow is not physical time; familiar interactions are not four exclusive size bands. The supplied examples do not derive all forces, biology, cognition or an AI advantage. [R-AUDIT, R-MATH]

A stationary point may be unstable. A stable bound structure need not consume external power continuously; a maintained open system may require ongoing flows. New *effective* modes are not independent microscopic degrees of freedom created from nothing. Use model-specific claims and conditions, not universal slogans.

## 4. Content, identity and publication contracts

All functions and fields in this section are **NEW/SELECTED interfaces**, not claims that an implementation already exists. Use the installed Astro collection API to validate the same contracts; do not duplicate schema definitions in scripts and components.

### 4.1 Stable scientific records

Use permanent IDs from the previously discussed families:

| Prefix | Role | Important distinction |
|---|---|---|
| UT-D | Definition | A chosen meaning, not an experimental finding |
| UT-A | Assumption | A premise of a specified model |
| UT-R | Derivation / restricted worked result | Must name assumptions, evidence and limits |
| UT-C | Conjecture | The claim being tested, not a statement certified by its examples |
| UT-E | Evidence / established-science connection | Must identify the particular externally supported claim |
| UT-P | Prediction | Expected observable outcome under explicit conditions |
| UT-F | Falsification / failure test | Must identify the target claim and scope of a negative result |
| UT-O | Open problem | Unresolved work; not a promise of eventual success |

IDs use schema **`^UT-[DARCEPFO][0-9]{2,}$`** with no spaces. The type must match the prefix. Allocate unused IDs; never recycle one to mean something different. Inspect the actual current files for existing identifiers before allocating new navigation IDs. Reuse source IDs or create an explicit mapping; never renumber the source meaning or assume R2 invented IDs already exist in RRG_CURRENT.

Required record fields:

```yaml
id: UT-D01
kind: definition
revision: 1
label: Geometry
contentOrigin: source-bound
sourceBinding: null  # fill only from an actually read current excerpt; example is not publishable
statement: null      # extracted at build time for source-bound records, not independently authored
plainLanguage: "Reviewed explanation of the same meaning."
scope: "What this definition or claim includes and excludes."
evidenceState: not-applicable
publicationState: draft
sourceRefs: [R-CURRENT-CORE]
dependsOn: []
related: []
```

For `contentOrigin: source-bound`, bind `sourceKey`, raw `sourceSha256`, actual `startLine`/`endLine` and an `excerptSha256` computed from the raw line slice. The published `statement` is extracted from that source, not freely editable in a record. A missing, changed or ambiguous binding fails. Use the original text once; presentation may convert Markdown syntax without altering meaning. `plainLanguage` is separately reviewed derivative prose.

For `contentOrigin: proposed`, an authored statement is allowed with proposal provenance, scope and an explicit non-adopted status. It cannot replace a locked definition or supersede a current claim solely by being published. Conditions and explanatory reasoning remain bound to their actual sources; proposal text is not silently injected into the current package.

The Markdown body holds supplementary conditions, reasoning, qualifications and source discussion. No placeholder example above is publishable content. Conditional fields include `assumptions`, `testRefs`, `supersedes`, `supersededBy`, `correctionRef`, and `evidenceRefs`. A derivation/result requires assumptions, a derivation or test reference, and explicit limits; an external-supported record requires identified external sources and their support scope; a project-reproduced record requires an actual execution receipt. A prediction requires observables and conditions; a falsification test requires its target ID, procedure and scoped rejection criterion. Supersession/withdrawal requires a change record and replacement information where applicable. A record may report a failed/contested test without pretending that it is a successful derivation.

Evidence state is independent: `not-applicable`, `external-supported`, `project-reported`, `project-reproduced`, `proposed`, or `contested`. Review state is derived from review receipts: `pending`, `accepted`, or `stale`. Publication state is `draft`, `published`, `superseded`, or `withdrawn`.

Display these as ordinary words: **Definition**, **Assumption**, **Established external result**, **Reported project calculation**, **Reproduced restricted calculation**, **Conjecture**, **Open question**, **Corrected**. Do not display a giant internal enum string. A definition must not receive an “Established science” badge just because it was approved for publication. A reproduced calculation must say the model scope alongside its result.

`dependsOn` means logical/semantic dependence and is acyclic. Physical feedback does not imply a cyclic proof. Use `related` for non-logical cross-links; these may be cyclic. Distinguish a bibliographic key from a project-source key and from a scientific record ID.

### 4.2 Documents and minimal structured reuse

Every newly authored publication page/example/article has the metadata below. Original RRG_CURRENT Markdown files receive equivalent route/ID/review metadata in `canonical-documents.yaml`, **not frontmatter written into their original bytes**. The adapter reads the actual source file through the same validation/publication path and hashes the source plus sidecar.

```yaml
id: DOC-START
route: /start/
title: "Start with the idea"
description: "A plain-language introduction to the research question."
kind: intro
lang: en
audience: general
publicationState: draft
researchEdition: working
publishedAt: null
updatedAt: 2026-10-01
dependsOn: []
sourceRefs: []
```

`id` is stable across a route rename. Route uniqueness is checked across document, record and generated utility routes. `kind` includes intro, concept, example, framework, mathematics, research-status, open-problems, article, about, contribute, library and licensing. Generated reference/search/feed/404 routes are owned by their code rather than pretending to be scientific documents.

For articles, `publishedAt`, tags and an approved displayed author/project identity are required when published. Dates must parse as real dates; `updatedAt >= publishedAt`. A published article later than the release's explicit timestamp is an error, not an automatically scheduled publication. Ordinary rebuilds must not make hidden content appear because the wall clock advanced.

Selected tiny Markdown extension:

- `:claim[UT-D01]` produces an inline link to the record.
- `::claim{id="UT-D01" view="plainLanguage"}` produces the current canonical plain-language statement and a record link. `view` is either `plainLanguage` or `statement`.
- `:cite[BIB-0001]` produces a bibliography link and records a source dependency.

Unknown directives, attributes, IDs or views fail validation. The extension produces normal safe Markdown/HTML nodes from schema-validated strings. It cannot load files, execute expressions, import modules, fetch a URL or interpolate arbitrary HTML. The Markdown export converts these directives into ordinary text/links so the download remains usable outside the website.

Narrative prose may paraphrase a concept, but it must declare relevant `dependsOn` IDs. Directives automatically add their IDs. The union is the real dependency set. A page-level source list is not a substitute for a citation adjacent to a material factual claim.

### 4.3 Source and evidence identity

`references.yaml` owns external bibliographic identities. Keep historical S01–S16 meanings within their original audit scope; do not assign global meaning to a bare S01 before reading the current evidence documents. Map `(sourceKey, localCitationKey)` to a stable bibliography ID such as `BIB-0001`. Deduplicate only by verified bibliographic identity, not matching local key or title fragments. Preserve original source text and local citations through the rendering adapter. A collision or unresolved alias fails publication.

`source-index.yaml` records actual path, raw hash, edition/date where known, role, availability and inspection scope. Current keys are defined in §3.1. Old `R-BASE-*`, `R-AUDIT`, `R-MATH` and result/code keys remain **historical**. The two `P-*-NOTE` entries are authority/update notices with `authorityNoticeOnly: true`; they cannot supply a missing current definition, primary scientific evidence or a computed core hash.

Keep three distinct observations: **declared current**, **bytes available**, and **verified against source/binding rules**. A file name or remembered sandbox link satisfies none of the byte-verification requirements. Exact raw core hashing is separate from LF-normalized semantic display hashing.

Historical numerical evidence, when intentionally included as a supplement, records input/script hashes, actual execution date and environment, command, parameters/seeds, output hashes, tolerances, reached checks and limitations. Original outputs are not overwritten. A new execution produces a new receipt; old R2 results remain attributed to that earlier run.

Do not hard-code numbers separately in components. The optional response-closure supplement imports validated data and checks all four exact-error bounds and metadata through a wrapper if selected. Do not execute research scripts during an ordinary site build. Availability of that old script does not make it the current mathematical programme or a mandatory replacement for `03_mathematical_core.md`.

Actual current 06/07/08 claims must be traced to their own source paragraphs, references and stated support limits. A title containing “proof” does not automatically make each entry a proved theorem. This alignment does not claim a fresh review of the papers named in the shared note.

### 4.4 Definition drift: exact mechanism and honest limit

Implement these shared operations in `source-admission.ts`, `publication.ts` and `content.ts`; all callers use the same validators:

| Operation | Input | Output / failure |
|---|---|---|
| `qualifyCurrentSource()` | Actual RRG_CURRENT bytes, selected edition/pin, predecessor/change record when revised, manifest and admission seal | Verified current-file inventory or typed missing/mismatch/incomplete failure; legitimate documented new editions are allowed, never legacy fallback |
| `loadCanonicalCorpus()` | Admitted current files + sidecars + publication Markdown/registries | Validated source-bound corpus; reject invalid excerpts, duplicate IDs, unknown references and unsafe paths |
| `dependencyClosure(entryId)` | Direct references extracted from content plus declared dependencies | Deterministic sorted transitive dependency set; reject missing IDs and proof-dependency cycles |
| `semanticDigest(entry)` | Canonical data + LF-normalized body | SHA-256 excluding only review/procedural fields; no mutable timestamp shortcut |
| `reviewFingerprint(entry)` | Own digest + dependency digests + relevant evidence/source hashes + rendering-policy revision | Exact digest of what was reviewed; no inclusion of its own receipt |
| `selectPublication(corpus, config, reviews)` | Valid corpus, fixed release identity/time, review evidence | Explicit published manifest or typed failure; no silently skipped stale published page |
| `render/export(manifest)` | Same selected entries | HTML, bibliography, feeds, search inputs, downloads; never reread an alternate content tree |

Serialization is deterministic: JSON object keys sorted recursively; array order preserved where meaningful; date values normalized; text line endings normalized to LF. Include all substantive record/page metadata and body. Exclude generated hash fields, reviewer names/signatures and review timestamps from the entry's own digest to avoid self-reference. A change in dependency metadata that is conservatively counted as substantive may trigger an extra review; it must not be silently ignored to reduce work.

A source-bound entry includes its actual source-file hash, excerpt hash and mapping in the fingerprint. Core bytes are hashed raw for admission; never normalize them to make an integrity mismatch disappear.

Hash the relevant individual bibliography/source records, not the whole YAML file, so an unrelated new reference does not make every page stale. Include changes to a referenced source's verification scope, evidence and identity.

A review receipt records `entryId`, fingerprint, reviewer kind (`agent` or `human`), review date, outcome and evidence reference. Scripts print the new required fingerprints and affected entries; **they do not auto-approve them**. Only the review task may record an accepted review after reading the actual affected material. A different model session is still an agent, not a fabricated human reviewer.

When a definition or result changes, reverse dependencies identify all affected published documents. Their old fingerprints become stale. Production build fails until those entries have been reread and reviewed against the changed meaning, or explicitly changed to a non-published state with the appropriate correction history. Do not simply copy a new digest into every receipt.

This mechanism detects unreviewed changes and stale dependencies. **It cannot prove that a paraphrase is scientifically faithful, that every implicit dependency was declared, or that a reviewer actually understood a source.** Semantic review remains mandatory. It is an accidental-drift guard, not a cryptographic truth or authorization system; repository/owner permissions remain the trust boundary.

### 4.5 Semantic changes and source fidelity

Sources may be changed; they must not be changed silently. Keep one current source rather than a “corrected” website copy that diverges from it. The owner permits justified necessary source/core revisions within the authorized task (§0.3). A check or reading task alone is not an instruction to alter science.

**Revision record.** Use the existing source change log where it can express the record. A website-side record may link to it; do not create two independently maintained decisions. Record: `changeId`, `category` (wording / factual-mathematical correction / evidence-status / definition-core / format / supplied-baseline), exact prior source edition/hash, affected files and claim IDs, concrete problem, proposed before/after meaning, rationale and support, permission basis/task scope, dependent documents, tests/review actually performed, and resulting edition/hash. Permission may be the owner's standing in-scope instruction; do not invent a new human approval for each edit. The permission basis must be a real instruction, not an agent asserting that it has permission.

**One revision path:** read the baseline and dependencies → explain why a source change is needed → preserve the previous edition in Git or an exact snapshot → edit actual current sources and their manifest/status/proof records coherently → update dependent excerpts, examples and articles → run affected checks after the complete batch → obtain the normal independent review → seal the new edition and keep predecessor provenance. Update only affected reviews; new hashes never auto-approve changed claims. A changed core may require broad dependent review, but no unrelated numerical or browser rerun is imposed merely because a version number changed.

For an owner-supplied replacement baseline, record its actual supplied identity and the meaningful differences from the previously inspected edition. When the old actual bytes are unavailable, state that comparison limit instead of fabricating a diff; the old note's hash is only a reference. Inspect the new complete file set and internal links before admission. A legitimately selected new baseline is not rejected solely for differing from the historical pin. Unexpected corruption or an unrecorded edit still fails admission. Retired filenames/claim IDs get deliberate migration and historical pointers; no automatic ten-filename assumption overrides a genuine documented edition change.

The current core's “locked” label protects against unannounced drift. It does not forbid a reasoned revision. Do not replace the overall research purpose with an easier project, silently fill missing arguments, inflate a claim's evidence status, or perform an unrelated rewrite. Such choices remain proposals unless genuinely within the owner's selected task. Sources being supplied does not by itself prove their scientific claims.

Initial reconciliation must show actual meanings and edition; current claim/status/proof IDs; coverage of both declared evidence files; the disposition of historical proposals; and how simple examples map to current claims. Until actual current bytes are read these are intake items, not scientific decisions. Old same-family criteria, `(G,z,χ;B)` descriptors and narrowed objectives are not made current merely by age or filename. Keep the environmental-enabling explanation and effective-interaction question at the appropriate depth unless a justified explicit research revision changes them. Preserve the distinction between a useful analogy, a hypothesis and demonstrated support.

For a genuine source error discovered during a revision task, fix the source with evidence and an explicit record rather than freezing the error in place. During a review-only task, report it and qualify/withhold the affected publication without rewriting the supplied source. Never edit a third-party publication or an already-issued historical snapshot to make it appear that it originally said something else. Keep private conversation details out of public change logs; public rationales describe the substantive change.

### 4.6 One publication filter for every surface

Production selection is explicit:

```text
admit actual RRG_CURRENT / verify raw core and full source edition
→ load/validate source-bound corpus
→ validate release config and real identities needed by selected surfaces
→ for every intended published entry:
     reject future publication dates
     require a valid exact review fingerprint
     require publishable dependencies and known sources
     require matching rights/provenance declarations for distributed assets
→ generate the published manifest
→ generate routes/nav/feeds/sitemap/exports from it
→ index only opted-in published reading bodies
→ audit the final output tree and bytes
```

The actual research release is never eligible while the current-source gate is open. Preview/test fixtures may exercise the same code with an explicitly synthetic, non-deployable corpus, but cannot satisfy actual-current-content acceptance. Summary transcriptions and historical artifacts do not make a missing current source optional.

Rules:

| State | Direct HTML | Navigation / search / sitemap / RSS | Downloads |
|---|---|---|---|
| Draft | Absent in production | Absent | Absent |
| Published current | Present | Eligible; articles only in RSS | Approved export set only |
| Superseded | Present only as explicitly retained historical page with prominent correction/replacement | Excluded from normal discovery feeds; linked from change history | Explicit historical export only |
| Withdrawn | Reason/date/replacement tombstone at old stable route; no old body | Excluded from normal discovery feeds | No current body export |
| Preview/test fixture | Local/private only | Never production | Never production |

`noIndex` is not a secrecy flag. A public GitHub repository exposes committed source, including files excluded from the website. Do not put private drafts, credentials, personal correspondence or sensitive invention details in that repository expecting a build filter to hide them. Keep such material outside the public checkout or in a separately authorized private source. History retention has a privacy/security exception: harmful disclosure can require removal/redaction and a non-sensitive correction record; “never delete anything” is not a safe absolute rule.

### 4.7 URL contract and output boundaries

`config/site.json` holds `origin`, `basePath`, repository owner/name and optional approved contact/credit fields. Production requires a real supplied target; local fixture configs use reserved `.invalid` origins and cannot pass the public-deploy gate.

Internal route input is a base-independent path. `withBase('/start/')` yields `/start/` for root and `/unity-theory/start/` for that project base; `withBase('/')` yields the base root with a trailing slash. File endpoints such as `/rss.xml` do not gain an extra slash. Normalize the configured base once. Reject traversal, protocol-relative URLs, duplicate slashes in configured routes, encoded traversal, and normalized/case-folded collisions. External HTTPS links are not base-prefixed.

Use the same URL owner for navigation, Markdown internal links, citations, images, canonical metadata, Open Graph links, RSS, sitemap, Pagefind bundle/base URL, downloads, source permalinks and 404 navigation. Canonical URLs are absolute and built from origin + normalized base + route, not manually pasted into each document. Citation source links bind the exact source commit; links labelled “edit/current source” may point at the working branch and must say so.

Markdown relative file links are resolved against the source file, checked to stay within the allowed corpus, then converted to that target's route and anchor. The output-link audit verifies actual emitted IDs rather than guessing GitHub's heading algorithm. Important definition/result anchors use explicit stable IDs generated by the renderer. Ordinary headings use the installed renderer's slugging result.

Only current public entries and reviewed static assets enter `dist/`. Do not copy the full repository, handoff, raw source tree, review notes or evidence working directory into `public/`. Download generation uses an explicit allowlist. No `.git`, `.env`, draft fixture, private source or administrative plan is a website asset.

### 5.2 Design system

Use a restrained editorial design, not a cosmic marketing aesthetic. Select one CSS token system in M2: prose width 66–72ch, desktop side navigation only on technical pages, approximately 18px body text, comfortable line spacing, clear headings, distinct but quiet status panels. An equation plot must identify its model and actual data source. Do not invent observational imagery or unexplained decorative graphs.

Each difficult concept follows **plain-language meaning → concrete example → formal definition → equation/limits**. ### 5.3 Accessibility and no-JS reading

Target WCAG 2.2 AA for the selected implementation, not a certification from a tool score. Use semantic landmarks, skip link, one meaningful H1, ordered headings, visible focus, real buttons/links, informative alt text, reduced-motion support and a usable 320-CSS-pixel layout. Essential explanation never depends on hover, color, animation or JavaScript. Native `details/summary` is acceptable for optional technical depth, but not for hiding the main uncertainty/status. [W6, W7]

Math uses KaTeX's HTML+MathML output, `trust: false`, bounded macro expansion and strict rendering failure detection. Load its CSS/assets locally only where needed. Keep a fresh macro environment per document so one article cannot redefine later articles' symbols. Unsupported or malformed current math fails the build; it must not silently become an error-colored “rendered equation.” The whole page must not scroll sideways; a genuinely long equation/table may have a labelled local scroll area that keyboard users can reach. [W5]

Raw HTML and MDX imports in authored research Markdown are rejected. Validate destination protocols and image assets. Inspect uploaded SVG as active content: no scripts, event handlers, foreign objects or unapproved external references. Trusted rendering transformations must not accidentally strip MathML or duplicate every equation in screen-reader output.

Search can require JavaScript, but `/search/` must provide a clear no-JS fallback to the topic/document indexes. Main navigation remains functional without client code. No analytics, tracking pixels, third-party font requests, external embedded widgets or on-site submission form in V1. External links, including GitHub issues, are ordinary links; no comment iframe.

### 5.4 Adopted performance budgets and qualification

- Home/ordinary reading pages: at most 15 KiB gzip of initial JavaScript; search code must not load until used.
- Home cold first-view transfer: at most 250 KiB gzip total owned HTML/CSS/JS/SVG/image assets. Report the accounting method and cache state.
- Math pages: report the full cold transfer including math assets separately; target at most 750 KiB gzip for the qualification page, not a silent exemption for remote assets.
- No autoplay media, full-page canvas or unnecessary hydration. CSS-only/native controls where sufficient.
- Run one Lighthouse production-build diagnostic on home and math under a recorded profile; target accessibility/performance issues rather than treating “100” as certification. Report LCP/CLS and the environment; field Core Web Vitals are NOT_MEASURED until actual field data exists.
- The 100-document/record/reference stress fixture must complete validation/build on the chosen CI runner without unbounded recursion or repeated filesystem/network reads. Record elapsed time and memory where available; no invented throughput claim.

A legitimate content requirement can justify a budget change, but it needs an explicit recorded design decision and comparable measurement—not a threshold quietly raised after failure.

### 5.5 Clarity evidence

Editorial review checks the first-screen sentence, the warm-up example, the distinction between real phenomena and a common hypothesis, and the connection back to environmental enabling. Count words/undefined terms as diagnostics, not a readability guarantee. Read the actual rendered mobile page aloud; cut repeated qualification panels and jargon where meaning survives.

Human validation is a separate, useful product check: ask at least two non-specialists to explain the idea, distinguish an example from proof, find a limitation and locate a source. Record actual answers and confusion, not invented quotations. Lack of such participants does not prevent engineering work; report **HUMAN_COMPREHENSION_NOT_TESTED** and never call an agent's opinion a user study. Authorial approval of the public introduction remains required for the first public release.

## 6. Lifecycle, build and release safety

### 6.1 Content update transaction

A change batch has this order:

```text
source/evidence or owner-directed meaning change under actual source change control
→ admit coherent current edition and verify locked-core pin / authorized change
→ update source bindings, derivative record revision and presentation change explanation
→ identify dependent documents through the graph
→ revise narrative and metadata where required
→ independent content review of resulting fingerprints
→ production selection / validation
→ build HTML + exports + search
→ audit emitted files and browser behaviour
→ authorize deployment of that artifact
```

An article proposing new science first creates/updates an explicitly proposed record with provenance and limits; adoption into the current theory follows source change control reconciled with §0.3/§4.5. It does not become the only place the new definition exists. A source withdrawal changes the source/evidence record and makes affected public claims stale; it does not merely remove a footer link.

A presentation-only change still requires its relevant rendering checks, but not a false new scientific result or unrelated experiment rerun. A scientific source/parameter/script change reruns the affected research checks and invalidates their old evidence. Do not rerun all historical numerical examples for every CSS change.

### 6.2 Typed failure behaviour

Distinguish `CURRENT_SOURCE_PACKAGE_MISSING`, `LOCKED_CORE_MISMATCH`, `CURRENT_MANIFEST_INCOMPLETE`, `SOURCE_BINDING_FAILURE`, `CONTENT_SCHEMA_FAILURE`, `REFERENCE_FAILURE`, `DEPENDENCY_FAILURE`, `STALE_REVIEW`, `SCIENTIFIC_REVIEW_BLOCKER`, `RIGHTS_OR_PRIVACY_BLOCKER`, `LINK_FAILURE`, `MATH_RENDER_FAILURE`, `BUILD_FAILURE`, `ACCESSIBILITY_FAILURE`, `ARTIFACT_MISMATCH`, and `DEPLOY_INFRASTRUCTURE_FAILURE`.

The three modes are `preview`, `qualification` and `release` (M0). Qualification uses the same reviewed selection, renderer and output checks as release, but can use a reserved fixture origin and explicit test identity; its artifact records `deployEligible: false`. Preview may expose drafts privately and cannot become a qualified or release artifact by renaming a file. Release additionally requires the real target and public authorization/identity/rights gates. No hidden bypass weakens semantic checks in qualification. A fixture corpus can test the mechanics, but its evidence states `corpusScope: synthetic` and `currentSourceQualified: false`; it cannot count as real-corpus qualification or be published as the current theory.
